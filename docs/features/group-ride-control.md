# Feature: Group Ride Control Center

**Status:** Phase 2 in progress  
**Owner module:** Group rides / trip workspace  
**Database:** `ride_participants`, `trip_invitations`, `location_updates`

## User outcome
Trip leaders can invite riders, assign sweep responsibilities and see a privacy-scoped roster. Riders accept invitations from inside RideNTrack. The live ride view distinguishes recent GPS updates from stale or missing updates.

## Invitation lifecycle
- Leaders create a token invitation with optional target email and role (`rider` or `sweep`).
- Default expiry is 72 hours; allowed expiry range is 1–720 hours.
- Tokens are UUIDs generated by PostgreSQL and only returned at creation time.
- Acceptance requires authentication. A targeted invitation must match the authenticated account email.
- Successful acceptance activates or reactivates membership and applies the invited role.
- Expired invitations transition to `expired` when acceptance is attempted. Revoked invitations cannot be accepted.
- Existing six-character ride-code joining remains available for backward compatibility.

## Roles and permissions
- The trip creator is bootstrapped as `leader` by the admin-join trigger.
- `sweep` and `rider` are assignable roles. A trip leader can issue invitations and change another active member's role.
- A second leader cannot be assigned through the participant role RPC; leadership transfer is not part of this increment.
- Invitation and role state transitions run in SECURITY DEFINER RPCs with fixed empty search paths and explicit authenticated-only execute grants.
- Roster reads are restricted to active trip members. Invitation records are visible only to the trip admin/leader.

## Roster status
The roster reports each active member's most recent persisted GPS timestamp:
- **Live:** last update is no more than 30 seconds old.
- **Stale:** last update is 30–120 seconds old.
- **Offline:** no saved GPS update or last update is more than 120 seconds old.

This is a GPS freshness estimate, not proof of network connectivity or whether a rider has physically left the group. Realtime Presence may improve instantaneous connection indication in a later increment.

## Current mobile implementation
- Trip workspace displays roster and role.
- Leader can create a 72-hour invitation, optionally target an email, choose rider/sweep and share the token using the native share sheet.
- Join screen accepts a private invitation token in addition to the legacy ride code.
- Leader can toggle an active participant between rider and sweep.
- Roster status is derived from latest persisted GPS update and is visibly labelled.

## Failure handling
- Unknown, expired, revoked, already-used and email-mismatched invitations are rejected.
- An expired token is marked expired and returns no trip ID.
- A failed invite or role change is shown in the trip workspace; membership is not changed by client-side state alone.

## Acceptance criteria
- [x] Trip admin is assigned leader on trip creation.
- [x] Invitations have optional email targeting, assigned role and bounded expiry.
- [x] Authenticated user can accept a valid token invitation.
- [x] Email-targeted invitations cannot be accepted by a different account.
- [x] Expired invitations cannot be accepted and are marked expired.
- [x] Only leader can issue invitations or assign sweep/rider roles.
- [x] Roster read is restricted to active trip members.
- [x] Regression tests cover RPC grants, acceptance, role assignment, roster and expiry.
- [ ] Live/stale/offline status verified against realtime presence and GPS on device.
- [ ] Route-deviation and rider-behind alerts.
- [ ] Regroup points and arrival confirmation.
